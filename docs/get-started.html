1. Choose your collection runtime.

The same collection solution offers multiple execution paths. Local Python and Azure Functions collection to local/Blob storage do not require a Fabric notebook. Containers are another packaging option; assess their scheduling and operational fit for your environment.

2. Set the boundaries before the credentials.

Choose the monitoring questions and modules first. Then review each module's scope and required permissions. Fabric Monitor is not Admin-API-only.

Authorization families are independent; one grant does not supply the others.
BoundaryWhat to review
Admin discovery and metadataEndpoint-specific Admin authorization, service-principal tenant settings and supported scanner metadata.
Non-Admin resource accessJob history requires item/job access; definition exports require item read/write access. A read-only collector can still require a role capable of modification. Admin discovery does not grant these rights.
Microsoft GraphSeparate application permissions and admin consent for selected directory/licensing data; group expansion is separately enabled and bounded.
Output storageIndependent local filesystem or Azure storage authorization. API access does not authorize storage writes.

For an Admin-only trial, deliberately choose modules in the Admin row of the API scope matrix. The default module list is not an Admin-only configuration. Keep secrets in private configuration; never put them in the site, a notebook example or a recording.

3. Try a small, local collection.

Use an approved Python environment and follow the platform-specific setup instructions. From the repository root, install the declared dependencies:

python -m pip install -r requirements.txt

Prepare a private .env with the required TENANT_ID, CLIENT_ID and CLIENT_SECRET values. Set LOCAL_OUTPUT_PATH to a dedicated writable folder outside the repository. Select CLOUD_ENVIRONMENT and configure only the approved modules.

For example, after authorizing Activity and Catalog:

python -m app.monitor --env-file .env --modules Activity,Catalog

This invokes the selected modules subject to their scheduling and checkpoint rules. It is not a command to force every resource to refresh. LOCAL_OUTPUT_PATH takes precedence over Blob and Lakehouse output settings.

Local does not mean offline. This calls real authorized APIs. Keep all monitored capacities on for accurate collection and assessment. Local output isolates the storage destination, not the tenant being queried. Do not rely on DRY_RUN as an API or permission safety boundary.

4. Verify what was actually retained.

  • Invocation: did the intended host run, and were the selected modules eligible?
  • Authorization: did each API accept the intended identity? A successful token is not proof of resource access.
  • Output: did files and state land in the expected folder, not an old storage target?
  • Coverage: distinguish successful empty results, failed requests, unsupported resources and uncollected scope.
  • Time: check observation times, UTC folders, API history windows and retained state. A folder date is not always an exact observation timestamp.

A successful process exit does not establish a complete estate. Use the collector operations guidance for request gates, recovery and resumable progress.

5. Promote the operation, not just the code.

For hosted collection, establish an owner for runtime health, identity, network access, scheduling, storage, retention and recovery. Use the enterprise checklist alongside the deployment guide.

  • The Function host timer and per-module cron checks serve different purposes. A module cron does not create another host trigger; the current Function also runs on startup.
  • Managed identity for Blob Storage or Key Vault is separate from the configured API identity. It does not automatically grant tenant or workspace access.
  • Use one scheduler against a given output/state root. Preserve checkpoints and resource progress rather than guessing a reset.
  • Retention must account for evidence, module-local controls and validation history. Do not apply a blanket delete policy without reviewing the documented implications.
  • External collection avoids the Spark notebook runtime for that path, not host, storage, API or optional analytics costs.

Read managed identity and RBAC and updating safely before operational rollout.

6. Add Fabric analytics when it adds value.

External collection can stop at retained JSON. If you choose the Lakehouse analytics path, first arrange an explicit handoff of the collected evidence into the expected Lakehouse Files root. Blob output is not automatically a Lakehouse mount.

  1. Follow the numbered notebook walkthrough. Import the self-contained notebooks and attach the intended default Lakehouse.
  2. Preview the relevant Bronze transformations with WRITE_TABLES = False, inspect coverage and destination, then deliberately publish.
  3. For event investigations, follow the separate Silver/Gold publication runbook. Gold consumes published, ready Silver—not an unpersisted preview.
  4. Use notebook 26 for read-only selected-event investigation against published Gold. Report/model integration is a separate step, not an automatic side effect of publication.

The right first milestone

A small, authorized collection with known scope, correctly retained evidence and understood gaps. Add more collectors or analytics only when they help answer the next question.
