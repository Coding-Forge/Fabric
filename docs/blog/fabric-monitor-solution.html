Solution story

Fabric Monitor: turning Power BI and Fabric telemetry into governed reporting

Power BI and Microsoft Fabric administrators need a repeatable way to understand what is happening across the estate. Fabric Monitor provides that foundation: scheduled API collection, durable raw output, an Activity PBIP for audit telemetry, and a Catalog PBIP that turns workspace and semantic model metadata into an estate schema.

The problem

Fabric and Power BI estates grow faster than manual oversight can keep up.

As organizations scale Power BI and Microsoft Fabric, administrators quickly need answers that are hard to maintain manually: which workspaces changed, which artifacts are active, who is using content, where failures are happening, whether access patterns look healthy, and which reports or semantic models deserve attention.

The native admin experiences are useful, but many teams still need a governed data collection pattern they can schedule, store, curate, and report from using their own enterprise standards. That is the purpose of Fabric Monitor.

The solution

A monitoring accelerator for API-driven estate visibility.

Fabric Monitor is a Python-based solution that uses a service principal or managed identity pattern to collect telemetry from Power BI, Fabric, and Microsoft Graph APIs. The collected data can be written to local files, Blob Storage, ADLS Gen2, or Fabric Lakehouse paths depending on where the customer wants the raw system of record to live.

The solution is intentionally modular. Teams can run all modules or select only the workloads they need, such as activity events, catalog scans, refresh history, gateways, apps, roles, tenant settings, capacity metrics, domains, Fabric items, and Graph group membership.

Area What it helps answer
Activity What happened, who did it, where did it happen, and did it succeed?
Catalog What workspaces, artifacts, reports, datasets, tables, columns, measures, lineage, refresh schedules, and datasource metadata exist?
Access Who has access through roles, apps, groups, and activity patterns?
Operations Where are refreshes, gateways, capacity signals, failures, and risk indicators appearing?

Architecture

Collect, store, curate, and report.

The architecture is deliberately simple. Python modules collect API responses on a schedule. Raw outputs are stored durably. Downstream curation shapes those files into reporting-ready data. Power BI and Fabric reports sit on top of the curated model.

  1. Collect: Scheduled modules call Power BI, Fabric, and Graph endpoints with service-principal authentication.
  2. Store: Raw JSON outputs are written to local files, Blob Storage, ADLS Gen2, or OneLake-compatible Lakehouse paths.
  3. Curate: Activity and catalog data can be standardized into silver-layer tables for repeatable reporting.
  4. Report: The Activity PBIP provides audit pages, while the Catalog PBIP provides estate schema, workspace inventory, semantic model inventory, datasource, refresh, and drill-through pages.
Design principle:

Keep raw collection separate from reporting. This makes the solution easier to operate in enterprise environments because collection cadence, retention, data quality, and reporting refresh can be managed independently.

Reporting layer

The PBIP projects provide practical dashboard starting points.

The included Power BI Projects are structured as stable starting points rather than heavily hand-authored reports. The Activity PBIP focuses on audit telemetry. The Catalog PBIP focuses on the shape of the estate: workspaces, reports, semantic models, tables, columns, measures, datasources, refresh schedules, and drillthrough investigation.

  • Audit Overview: executive activity posture, volume, success rate, users, workspaces, and artifacts.
  • Activity and Operations: operation analysis, refresh activity, failures, and workload trends.
  • Users and Access: user behavior, client IPs, access investigation, and user type analysis.
  • Workspaces and Artifacts: workspace and artifact footprint, dataset activity, and capacity context.
  • Risk and Anomalies: failed activity, unusual IP patterns, suspicious operations, and high-volume users.
  • Drillthrough Detail: row-level investigation with user, workspace, activity, artifact, request, and success context.

Catalog PBIP

The Catalog PBIP answers estate schema and governance questions.

The Catalog PBIP is located at pbip-local\Catalog. Its semantic model reads catalog scan JSON and normalizes the metadata into tables for Workspaces, Reports, Datasets, Tables, Columns, DatasetMeasures, DatasourceInstances, DatasetDatasourceUsages, DatasetRefreshSchedules, DatasetRefreshScheduleDays, DatasetRefreshScheduleTimes, Dashboards, Dataflows, and Datamarts.

Use this PBIP after a catalog scan completes. Refresh the report against the scan output folder, start with Fabric Schema Overview, then move into Workspace Inventory, Semantic Model Inventory, and Data Sources & Refresh. Use the workspace and dataset drillthrough pages when a dashboard or table raises a governance question.

Page Use it to answer
Fabric Schema Overview How large is the estate across workspaces, reports, datasets, tables, columns, measures, and other artifacts?
Workspace Inventory Which workspaces exist, what state are they in, and which artifacts live inside each workspace?
Semantic Model Inventory Which semantic models have many tables, columns, or measures and may need design, ownership, or governance review?
Data Sources & Refresh Which datasource instances and gateways feed the models, and how are refresh schedules configured?
Workspace and Dataset Drillthrough What is the detailed schema, source, report dependency, and refresh context for a selected workspace or semantic model?
Practical governance use:

The Catalog PBIP can support workspace cleanup, semantic model review, datasource dependency mapping, refresh schedule rationalization, migration planning, and stewardship conversations with report/model owners.

Deployment

Run locally, in containers, in notebooks, or as an Azure Function.

For development, the monitor can run as a local Python application. For repeatable packaging, it can run in containers. For notebook-centric teams, it can be driven from Synapse or Fabric-style notebooks. For production collection, the recommended enterprise pattern is an Azure Function timer writing raw output to governed storage.

The solution also includes cloud profile behavior for Commercial, GCC, GCC High, and DoD. Commercial can use the full Fabric REST and OneLake path. Government profiles switch identity, Power BI, Graph, and storage endpoints while skipping Fabric REST and OneLake modules until the Fabric Gov surface is available.

Next steps

Use it as a foundation, then tailor it to the estate.

The value of Fabric Monitor is not only the first dashboard. The value is the repeatable telemetry foundation it creates. Once the collection and PBIP starters are in place, teams can extend the model with customer-specific governance rules, risk thresholds, workspace lifecycle policies, adoption metrics, catalog stewardship rules, and operational alerts.

Start by enabling the service principal, choosing the modules that matter, selecting the storage pattern, running an initial catalog baseline, and publishing the Activity and Catalog PBIP reports against curated activity and catalog data.
