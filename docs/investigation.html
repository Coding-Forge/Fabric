A synthetic, evidence-first walkthrough

An event is a starting point.
Not the whole story.

An audit operation references a pipeline. Can we connect it to a run, inspect retained activities, and explain what remains unknown?

Fictional example. E1, P1, C1, R1, A1 and all values below are illustrative shorthand, not tenant observations or executable sample input. This describes the implemented evidence model, not a claim that your environment contains these records.

The investigation

1. Frame the question2. Check Bronze3. Establish the links4. Follow the trace5. Handle missing evidence6. State the conclusionTry the workflow

1. Ask a question the evidence can answer.

Our fictional audit event E1 reports pipeline P1 and correlation value C1. We want to know whether retained job evidence contains a compatible run, and what activity observations exist for that run.

We are not starting with the assumption that an audit actor caused a physical data transfer or that every downstream dependency is known. Those are different claims requiring different evidence.

2. Check the retained evidence first.

Bronze is the collected evidence and the existing historical monitor_* tables. A collector poll is not a pipeline execution.

Fictional records available for this example
EvidenceRetained observationInterpretation
Audit record E1References P1; reports correlation C1.The provider reported the operation and identifiers.
Job record R1Belongs to P1; reports root correlation C1.A candidate observed execution, subject to exact identifier and scope checks.
Activity record A1References parent R1; reports 42,000 copied rows.A retained activity metric, not independently verified end-to-end movement.
Resource outcomesJob/activity polling coverage and timestamps.Context for what was attempted, what succeeded and how old observations are.

Job and pipeline-activity collection use non-Admin workspace/item Fabric APIs; Admin discovery alone does not grant resource access. Polling gaps, limited history, unsupported resources and denied access can prevent these records from being retained. The analytics notebooks cannot recover missing API history.

3. Connect identifiers. Don't guess by name.

Silver normalizes the evidence into scoped identities and links. An item named Daily Load in two workspaces is not the same item. Tenant, workspace and item identifiers matter.

  1. Normalize and deduplicate E1 while retaining its source-file references. Conflicting records are quarantined rather than arbitrarily resolved.
  2. Retain the explicit artifact reference to P1. Use historical inventory labels as context, not proof of the artifact's exact event-time state.
  3. Compare the audit ActivityId or RequestId to the job's root_activity_id. Require compatible explicit artifact scope.
  4. Accept E1-to-R1 only when the exact-ID match is unambiguous and artifact-compatible. Nearby timestamps and matching names are not fallback evidence.
  5. Retain A1 at its activity grain. Repeated polls of the same activity do not become additional copied rows.

Reported identity/IP values are suppressed by default in Silver. Keys do not verify a human identity. Redacted audit locations remain references; they are not relabelled as physical pipeline endpoints.

4. Follow the trace, with its limits attached.

Gold organizes published, ready Silver evidence into event cases, typed trace edges and separate execution/activity facts.

Audit event E1
  |
  +-- references --------> Pipeline P1
  |
  +-- exact correlation > Observed run R1
                              |
                              +-- activity > A1
                                             Reported rows: 42,000
                                             Physical source: unknown
                                             Physical destination: unknown

The trace supports inspection, not an automatically complete impact graph. Child-run traversal is cycle-safe and depth-capped; a capped result is flagged. If several events link to the same run, its activity metric must not be summed once per event.

A defensible finding

“E1 is exactly correlated with this observed run under compatible artifact scope. That run has a retained activity reporting 42,000 copied rows. The physical source and destination are not established by this evidence.”

5. What if the run or activity is missing?

Keep the event. Keep the unresolved reference. Investigate the collection boundary rather than inventing the missing edge.

Different gaps require different next steps
SituationWhat to doDo not conclude
No job observationsCheck job resource outcomes, permissions, supported item types, history windows and polling cadence.“The pipeline did not run.”
Several compatible candidatesPreserve the ambiguity. Review scope and source identifiers.“Pick the nearest timestamp.”
Activity has no metricKeep the metric null and examine available coverage.“Zero rows moved.”
New Silver preview; older published SilverCheck build IDs and publication readiness before Gold processing.“Gold must reflect the latest preview.”

A ready build means publication consistency checks passed. It does not mean complete collection. A valid snapshot can correctly contain no execution observations and explicit gaps.

6. State what is known—and stop there.

  • Supported: retained provider events, explicit artifact references, qualifying exact correlations, retained run/activity metrics and evidence gaps.
  • Not proven: human causality, physical source/destination, current state from old snapshots, complete effective access or distinct end-to-end row movement.
  • Still separate work: comprehensive dependency-impact closure and a new Silver/Gold semantic-model/report experience. Existing report projects do not automatically consume these investigation tables.

This is the value of an evidence-first monitoring system: a useful answer includes its confidence boundary, not just another number on a dashboard.
