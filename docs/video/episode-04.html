Two notebook roles

Collection and analytics are different jobs.

Collector notebook

Runs the Python monitoring code through env.notebook.run. Calls approved APIs and retains raw evidence plus collection controls.

Analytics notebooks

The numbered suite transforms existing Lakehouse files. Embedded helpers; no collector checkout or API credentials required.

nb_orchestrator runs transformations. It does not collect API data or schedule itself.

Prepare the collector runtime

Make the code and dependencies available.

Approved code

Provide the repository's collector package in the notebook environment. Pin the version used for acceptance.

Runtime dependencies

Validate the collector's requirements against the chosen environment. Check imports and network access before scheduling.

Default Lakehouse

Attach and verify the intended Lakehouse. Keep required execution and monitored capacities available.

The collector needs repository code and dependencies; generated analytics notebooks are self-contained.

Configure privately

API identity and scope

Resolve tenant, client and secret settings through an approved private mechanism. Select modules deliberately.

Runtime identity

Verify secret access, Lakehouse access and the identity actually used by manual and scheduled runs.

The helper does not load a .env file automatically. Environment settings can still participate in configuration.

Design the pipeline explicitly

Execution dependencies are not quality gates.

Collector notebook
  -> Review persisted evidence and coverage
  -> nb_orchestrator: selected transformations
  -> Review publication and validation

Deployment pattern

Create and accept the intended activities, dependencies, parameters, identity and failure behavior.

Coverage policy

Define how incomplete or stale collection affects downstream work. The supplied orchestrator does not implement that collection-quality gate.

Illustrative architecture, not a supplied or already deployed production pipeline.

The downstream analytics entry point

Preview first. Publish serially.

Shared parameters

RAW_ROOT / TABLE_PREFIX

Explicit permission mode
Selected notebook names and timeout

Execution contract

Same default Lakehouse for parent and children. Serial transformations. Visualization 05 and validation 06 are excluded.

Do not overlap orchestrators or other writers targeting the same prefix; domain notebooks share estate_coverage.

Accept the scheduled execution path

Manual success is not scheduled acceptance.

Identity and access

Verify scheduled code, secret, API and data access. Non-Admin features and Graph retain their separate permission boundaries.

Recovery and overlap

Validate timeouts, retries and failure propagation. Preserve checkpoints and cooldowns. Prevent competing collection and publication.

Operational outcomes

Review child-run details, coverage, freshness, costs and restricted logs. Define ownership and alerts.

A child marked Succeeded establishes execution success, not fresh or complete collection.
