The Azure Function App production path.

Deployment, identities, startup behavior and operational acceptance. No live provisioning or collection.

The hosted collection path

Separate runtime needs from collected evidence.

Function host

Documented Python 3.12 / Functions v4 Linux target. Select a suitable hosting plan and region.

Runtime storage

AzureWebJobsStorage supports the Functions runtime. Configure its access independently.

Data destination

Protected Blob / ADLS output for raw observations, retained state and collection controls.

Validate network reachability, invocation duration, quotas and costs for the selected environment.

Identity is not one permission

API identity and storage identity are separate.

Collector API credentials

TENANT_ID / CLIENT_ID / CLIENT_SECRET

Service-principal authorization remains endpoint-specific. Non-Admin features and Graph need separate approval.

Function managed identity

Use the documented identity-based storage pattern and approved Blob data access.

For a Key Vault reference, separately grant secret-read access under the vault's authorization model.

Managed identity for storage or Key Vault does not replace the current collector's API credentials.

Configure privately before deployment

Promote settings, not local PoC assumptions.

Approve the collection

CLOUD_ENVIRONMENT
APPLICATION_MODULES
API identity and module-specific scopes

Keep CLIENT_SECRET in an approved secret store, referenced privately.

Approve the destination

STORAGE_ACCOUNT_URL
STORAGE_ACCOUNT_CONTAINER_NAME
STORAGE_ACCOUNT_CONTAINER_ROOT_PATH

Remove unintended LOCAL_OUTPUT_PATH and OUTPUT_PATH overrides.

Do not deploy credential files or carry local AZURE_* environment credentials into the intended managed-identity pattern.

Know when execution starts

The current trigger also runs on startup.

schedule="0 0 2 * * *"
run_on_startup=True
use_monitor=False

Scheduled invocation

Daily at 02:00 UTC in the current repository code.

Startup invocation

Host startup can invoke collection before the next timer boundary, including after deployment or restart.

Approve collection before publishing or restarting. This trigger is not proof of durable schedule monitoring or non-overlap.

Review the artifact, then publish

Deployment is an approved change.

func azure functionapp publish YOUR_FUNCTION_APP

Core Tools path

Publish from the reviewed checkout to the approved app. Inspect .funcignore and the actual package for secrets, raw evidence and video artifacts.

Developer CLI path

The repository also supplies azure.yaml and Bicep. Validate templates, required files and parameters before provisioning.

Illustrative command only. The infrastructure guide reports compile validation, not completed live deployment acceptance.

Verify behavior, not just deployment

A successful publish is only the first check.

Host and identity

Trigger registration, storage access, secret-reference resolution and network reachability.

Collection outcome

Module results, persisted state and applicable manifests or resource outcomes. Missing evidence is not zero.

Operational visibility

Configured logs, exceptions and alerts. Application Insights where deployed and connected.

Review logs privately. An outer invocation finishing does not prove complete, fresh collection.

Before enabling routine operation

Keep recovery and retention deliberate.

Execution and recovery

Validate duration limits, startup behavior, overlapping writers, API cooldowns and failure recovery. Preserve checkpoints and quota controls.

Evidence lifecycle

Restrict data access, monitor storage growth and review retention. Keep monitored capacities available when collecting.

Optional Bicep retention replaces the storage account's management policy. Review it as a deletion change.
