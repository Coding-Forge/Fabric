Fabric Monitor / Episode 07

Operate deliberately.
Recover with evidence.

Production checks, fault isolation and safe continuation.

An operations extension to the six-episode foundation. Illustrative only: no live incident, requests, repairs or dashboard walkthrough.

The operating contract

Know what should run before judging what ran.

Approved scope

Record modules, permission mode, target scope, identities, code version and the intended output root.

Expected cadence

Confirm monitored capacities are on. Define freshness expectations per source and allow for bounded collection cycles.

Ownership and alerts

Assign an operator, failure route and recovery approval. Monitor duration, deferrals, coverage, storage growth and costs.

These are acceptance requirements, not an installed alerting system or a guarantee of complete tenant visibility.

Find the first broken handoff

Troubleshoot the layer that owns the failure.

Host invocation -> API collection -> retained raw evidence
  -> explicit Lakehouse handoff -> curated Delta publication
  -> derived model context, if used -> semantic model

Collect the timeline

Correlate UTC times, module/run/cycle, selected scope, manifests and the first relevant error.

Keep evidence private

Review and redact excerpts. Legacy logs, raw files, definitions and browser/network traces can contain sensitive metadata.

A model symptom is not permission to rerun APIs. Analytics notebooks do not collect fresh API data.

Execution is not coverage

Read the summary, then the evidence.

Succeeded

The module reported success and its checkpoint can advance after state persistence. Inspect actual scope and coverage.

Deferred

Saved progress can continue later; lastRun stays unchanged. An invocation with only deferrals can finish without raising failure.

Failed or incomplete

The success checkpoint does not advance. Successful sibling resources may still exist; they do not prove whole-cycle success.

A finished, complete resource with records=[] is successful-empty. Missing, unfinished or failed evidence is not zero.

When nothing new appears

Check invocation, eligibility and progress separately.

Host wakeup

The current Function trigger is daily at 02:00 UTC, with startup execution and use_monitor=False.

Module eligibility

Module cron is a UTC eligibility check at invocation time. It does not create another timer or continuous polling.

Bounded continuation

Permission scopes can need multiple invocations. Check persisted progress, cooldown and cycle health before resuming.

Restart or deployment can make real requests immediately. Use one scheduler per output root; do not loop restarts or overlap hosts.

Authentication and authorization

Diagnose the identity and endpoint, not just the code.

401: investigate authentication

Check the actual settings, cloud audience and credential validity privately. Legacy token-provider requests allow one renewal retry, not every collector path.

403/404: inspect context

Check endpoint support, resource identity and actual permissions. A status alone does not establish missing consent, deletion or unsupported item type.

Non-Admin boundaries

Jobs need item access; connections are caller-visible; deployment history needs pipeline Admin; definition exports need item read/write.

Separate identities

API client credentials, storage/Key Vault identity, scheduled notebook identity and model access are separate checks. Graph has separate consent.

Throttling and transient responses

Waiting is part of the protocol.

Legacy request transport

429/503/504 use a bounded retry budget. A valid Retry-After is not shortened by the fallback-delay cap. Shared cooldowns live within one runtime Context.

Four gated Fabric collectors

Request ledgers retain cooldowns across restarts. Permission retries defer to later invocations; other long waits can also defer.

Neither mechanism coordinates every tenant client. Do not increase concurrency or shorten server waits to force progress.

Blocked or ambiguous requests

Preserve the ledger. Do not guess a reset.

Under the configured output root:
  state.yaml                       success checkpoints
  <gated-module>/request_gate.json  cooldown / pending / blocked
  permission progress files        cursor / cycle health
  <module>/YYYY/MM/DD/runId/        manifests / resources
Pending may mean the server received the request. Stop scheduling, preserve evidence and escalate if a safe next-request time cannot be established.

Raw evidence to curated tables

Repair the handoff, not the history.

Find the same evidence

Confirm output precedence, approved copy/availability mechanism, default Lakehouse, RAW_ROOT, prefix and permission mode.

Respect write guards

Ownership, schema or hash rejection needs investigation. Do not drop tables, edit hashes or rewrite historical manifests.

Resume publication serially

After partial writes, investigate and rerun unchanged input/settings/prefix. Cross-table publication is not transactional.

Same-prefix concurrent notebook writers are unsupported. Preview first; approve writes separately. Bounded driver-side reads are not unlimited ingestion.

Retention and recovery planning

Protect what continuation and validation need.

Raw evidence and controls

Restrict access. Review lifecycle prefixes: module folders can contain both dated observations and durable controls.

Delta and baselines

Keep validation baselines immutable and retain their required Delta history. Do not vacuum or change retention during the experiment.

Optional Blob lifecycle deployment replaces the account policy. Root state exclusion does not mean every module-local control is protected.

When model results are blank or stale

Restore consistency before refreshing again.

Finish curated publication; keep competing writers idle
  -> validate selected source versions
  -> rebuild approved derived context, if that model uses it
  -> confirm readiness -> refresh/reframe -> verify measures

Check context and meaning

Inspect source selection, observation grain, date roles and coverage. In the inspected local model, readiness guards can intentionally blank measures.

Use a private target

Verify model/source identity and permissions. Do not attach to or overwrite a shared model by assumption; remote edits can persist immediately.

Close an incident with a bounded claim

Verify recovery at the layer that failed.

State the finding

Record affected version, time, scope, first failure and known gaps. Separate confirmed causes from hypotheses.

Approve and observe

Resume one authorized invocation only when gates permit. Verify persistence, cycle/coverage and the downstream handoff.

Retain the limits

API history windows can leave unrecoverable gaps. Offline tests or a stable rerun do not establish live freshness or tenant completeness.

Return to Episode 3 or 4 for hosting, Episode 5 for curation/validation, and Episode 6 for modeling. Dashboarding remains out of scope.
